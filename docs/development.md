# Development Guide

## Prerequisites

Node.js ≥ 20 and npm. Everything else installs locally.

## Setup and daily commands

```bash
npm install          # install workspace dependencies
npm run build        # tsc -b: builds + typechecks every package (project references)
npm test             # vitest run: all unit/integration tests
npm run typecheck    # alias of build (composite projects emit while checking)
npm run typecheck:tests  # strict-typecheck all test files (vitest alone does not)
npm run format       # prettier --write
npm run lint         # prettier --check + build + test typecheck
```

Tests import workspace packages by name (`@dl-sentinel/core`) — the root vitest config
aliases them to `src/`, so tests do not require a prior build. Running the CLI or API for
real does: `npm run build` first, then `node apps/cli/dist/main.js`.

## Conventions

- ESM everywhere; **relative imports must end in `.js`** (NodeNext resolution), e.g.
  `import { x } from './util.js'` even though the source file is `util.ts`.
- Prefer `import type { ... }` for type-only imports.
- Strict TypeScript is on (including `noUncheckedIndexedAccess`); no `any` unless
  narrowly justified with a comment.
- Tests live in `<package>/test/*.test.ts`; cross-package tests in `tests/`.
- No placeholder or tautological tests. Every scanner rule ships a positive and a negative
  fixture.
- Zero new dependencies without lead approval. Approved runtime deps today: `yaml`.
- Do not commit: build output, `node_modules`, editor/agent state, environment files,
  `package-lock.json` changes from feature branches (the lead regenerates the lockfile at
  integration).

## Parallel development model

Work is split across instances, each owning a branch and an exclusive set of paths:

| Branch                            | Scope                       | Owned paths |
| --------------------------------- | --------------------------- | ----------- |
| main (lead)                       | contracts, root configs     | root files, `packages/core/`, `docs/architecture.md`, `docs/scanner-interface.md`, `docs/finding-schema.md`, `docs/development.md`, `.github/` |
| feature/sentinel-core             | scan engine                 | `packages/engine/` |
| feature/sentinel-testing          | test framework & fixtures   | `tests/` |
| feature/sentinel-docs             | user documentation          | `README.md`, `docs/getting-started.md`, `docs/scanners.md`, `docs/rules.md`, `docs/configuration.md`, `docs/cli.md`, `docs/api.md`, `docs/contributing.md`, `docs/security.md` |
| feature/sentinel-secrets          | secrets scanner             | `scanners/secrets/` |
| feature/sentinel-dependencies     | dependency scanner          | `scanners/dependencies/` |
| feature/sentinel-source           | source code scanner         | `scanners/source/` |
| feature/sentinel-infra            | docker/infra scanner        | `scanners/infra/` |
| feature/sentinel-api              | API definition scanner      | `scanners/api/` |
| feature/sentinel-smart-contract   | smart contract scanner      | `scanners/smart-contract/` |
| feature/sentinel-cli              | CLI                         | `apps/cli/` |
| feature/sentinel-reporting        | report renderers            | `packages/reporting/` |
| feature/sentinel-dashboard        | web dashboard               | `apps/web/` |
| feature/sentinel-backend          | HTTP API server             | `apps/api/` |

Rules:

1. Never modify paths owned by another branch. If you need a change there, note it in your
   handover; the lead coordinates.
2. Never modify root configuration files (package.json, tsconfig\*, vitest.config.ts,
   .gitignore, CI). The workspace is pre-wired for every package.
3. Do not merge branches yourself; the lead integrates in wave order.
4. Run the relevant tests before handover and report honest results.
5. Keep commits scoped and conventional: `feat(engine): isolate scanner failures`,
   `test(secrets): add credential fixtures`, `fix(cli): correct sarif exit code`,
   `docs(api): document scan endpoints`.
6. Commits must not contain tool-generated attribution trailers of any kind (no
   `Co-authored-by:` for tools, no "generated by" lines). Commits appear as normal project
   commits by the configured git user.

## Definition of done (per feature)

- Implementation complete; no stubs left in owned paths.
- Unit tests added (positive + negative + error cases); integration tests where relevant.
- Security implications considered (redaction, no code execution, bounded input).
- `npm test` and `npm run build` pass locally.
- `npm run format` applied.
- Diff reviewed; only intended files committed; branch clean (`git status` empty).
- Documentation for the area updated if the area owns docs.

## Handover format (end of every instance's work)

```text
## Completed
- ...

## Files Changed
- path ...

## Tests
Command: <exact command>
Result: PASS/FAIL (numbers)

## Known Issues
- ... (or "None")
```

## Integration checklist (lead)

```bash
git fetch --all && git status && git diff --check
npm install                 # regenerate lockfile once per wave
npm run build && npm test && npm run format:check
```

Plus: review each branch diff before merging, verify no attribution trailers or agent
state files entered history, verify no secrets in fixtures beyond obviously-fake values,
and re-run the full suite after each wave's merges.
